## Build from source

1. Check out the FlagTree branch and a separate AscendNPU-IR tree at the actual compiler pin. Run `bash repro/restore_a5.sh consumer WORK COMPILER_CHECKOUT CANN_ROOT 16` from this records directory. The script starts at the LLVM source tree, with no historical CMake cache. It applies `pinned-compiler.patch`, `r7-matmul-namespace.patch`, `r8-arith-aptype-gcc.patch`, `r9-static-link.patch`, and `r11-gather-cbuf-abi.patch` in order. The GitCode TCB patch is for its own baseline.
2. Run `bash repro/restore_a5.sh producer WORK FLAGTREE_CHECKOUT LLVM22_SDK PYTHON CANN_ROOT 16`. The script uses the explicit Python interpreter and LLVM 22 prefix. Follow the checkout's producer dependency declarations for optional features. Install the matching Ascend backend libdevice at the path reported by get_libdevice().
3. Keep the two invocations serialized or use the same work directory lock. The scripts accept 16–32 jobs. Use the two tools from the same consumer prefix. The script stages CANN c310 meta-op bitcode in its lib directory and emits separate SHA256 manifests for producer and consumer.

- The exact LLVM 22 SDK package used on A5 is `llvm-f6ded0be-3f5016d1-ubuntu-arm64.tar.gz` from the Triton Ascend LLVM builds archive. The SDK records its download locator in version.txt. Use the exact AArch64 package from the [Triton Ascend SDK archive](https://triton-ascend-artifacts.obs.myhuaweicloud.com/llvm-builds/llvm-f6ded0be-3f5016d1-ubuntu-arm64.tar.gz). The package reports LLVM 22.0.0git, AArch64 host, NVPTX/AMDGPU/AArch64 targets, RTTI off and assertions on. Check its tools against ARTIFACTS_A5.sha256 before using it. The consumer SDK is regenerated by the LLVM 19 path in restore_a5.sh. To install an SDK as well as build the host tools, run the install target in that same configured build.
- Ascend libdevice comes from the FlagTree Ascend packaging dependency for release/3.6.0. The URL is defined in `python/setup_tools/utils/ascend.py`; the expected Git blob is `aa92cc6564bdba4635bdef1d193432dfaedf3036`. Place it at `third_party/ascend/backend/lib/libdevice.10.bc` after verifying ARTIFACTS_A5.sha256.
- Current build references were produced with AArch64 Ubuntu GCC 11.4.0, CMake 4.4.4, Ninja 1.13.2 and Python 3.12.16. The replay interpreter must import torch and torch_npu. Check that before running on a device.
- GitCode feature commit `3f8c7c37420ecbd366ddf7484fc24933d23a55a4` is based on the GitCode TCB branch. The host build uses the exact compiler pin and the R11 patch from FlagTree.

### Reproduce without the original captures

Set FLAGTREE and COMPILER_SOURCE to the two checkouts, CONSUMER to WORK/llvm19-bishengir, PRODUCER to WORK/flagtree, PYTHON to the replay interpreter, and CANN_ROOT to the pinned CANN installation. Choose writable paths for ASSETS, RESULT and DEVICE_LOGS, and set NPU_ID to the allocated physical device. Use absolute paths for the filesystem variables. Run from this records directory after restoring the consumer and producer.

```bash
mkdir -p "$RESULT"
bash repro/build_gather_device_bc.sh "$FLAGTREE" "$COMPILER_SOURCE" "$CANN_ROOT" "$ASSETS"
BC="$ASSETS/gather-normal.bc"
LIBDEVICE="$FLAGTREE/third_party/ascend/backend/lib/libdevice.10.bc"
for dtype in fp16 bf16; do
  "$PYTHON" repro/make_gather_fixture.py "$dtype" "$BC" "$RESULT/$dtype.mlir"
  bash repro/compile_gather_adapter.sh "$CONSUMER" "$CANN_ROOT" "$BC" "$LIBDEVICE" \
    "$RESULT/$dtype.mlir" "$RESULT/$dtype"
done
"$PYTHON" repro/make_gather_fixture.py fp16 "$BC" "$RESULT/producer-fp16.mlir" --producer-syntax
"$PRODUCER/bin/triton-mlir-opt" "$RESULT/producer-fp16.mlir" --mlir-print-op-generic \
  -o "$RESULT/fp16.ttadapter"
bash repro/replay_gather_device.sh "$FLAGTREE" "$PRODUCER" "$PYTHON" "$CONSUMER" \
  "$CANN_ROOT" "$BC" "$RESULT/fp16.ttadapter" "$RESULT" "$DEVICE_LOGS" "$NPU_ID"
```

The two synthetic fixtures passed offline ABI checks. The serial hardware replay ran the FP16 and BF16 variants on A5 using the AIC bitcode and AIC launch metadata, with three launches per index pattern. ARTIFACTS_A5.sha256 records reference hashes for the inputs and offline outputs. Rebuilding on a different path or toolchain can change output hashes. Use the per-run manifests to check the actual selected inputs and outputs.

The standalone producer probe in `repro/r11_gather_replay.py` runs with `R11_PRODUCER_ONLY=1` and a fresh TRITON_CACHE_DIR. Pass the same flags and Python paths as the replay launcher, together with R11_FLAGTREE, TRITON_BUILD_DIR, R7_BISHENGIR_ROOT and R11_GATHER_BC. It stops at the TTIR boundary and performs no NPU launch.

For the R12 32x64 regression, append `--tile 32 --cols 64` to each fixture-generator invocation above and set `R12_TILE_SIZE=32 R12_COLS=64` for the replay. The replay checks six index patterns. The build target `AscendCustomOpsBitcode` includes both AIC-only and Mix Gather L1 bitcode in the c310 family asset. Keep the formal Registry gate until the normal JIT and device launch metadata are validated.
